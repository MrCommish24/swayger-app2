We are now implementing the first presentation-only phase of the Swayger Run.

# SWAYGER RUN V1A — PREMIUM WEEKLY PLAY UX

This is an implementation task.

We previously completed the Swayger Run UX assessment.

Important architectural conclusion:

V1A can be implemented as a presentation-layer enhancement over the existing Weekly Fantasy play architecture.

V1A must NOT change:

- prediction semantics
- published Weekly props
- answer options
- scoring
- settlement
- League Picks logic
- Weekly Results
- Weekly Receipt
- Call Your Shot privacy
- participant identity
- database schema

NO SCHEMA CHANGE is expected for V1A.

My Lock is NOT part of this build.

==================================================
1. PRODUCT GOAL
==================================================

We want Weekly Fantasy play to feel less like filling out a form and more like completing a short branded game session.

Product concept:

THE SWAYGER RUN

One Moment at a time.
Every call gets acknowledged.
Progress builds visibly.
Completion gets a payoff.

UX north star:

LESS LIKE FILLING OUT PICKS.
MORE LIKE PUTTING YOUR TAKES ON THE RECORD.

The new experience should feel:

- premium
- focused
- responsive
- lightweight
- distinctly Swayger
- low-friction

Do not overbuild.

==================================================
2. V1A SCOPE
==================================================

Implement only:

1. Pilot feature gating
2. One-card focus mode
3. First-unanswered resume behavior
4. Dynamic Swayger meter
5. Server-confirmed acknowledgment microinteraction
6. Lightweight haptics
7. Stronger completion payoff
8. Compact review/edit summary
9. Accessibility improvements
10. Minimal analytics extensions
11. Easy rollback path

- My Lock
- My Lock persistence
- My Lock UI

- scoring changes
- XP

- streaks

- elaborate animations

==================================================
3. FEATURE FLAG / ROLLBACK REQUIREMENT
==================================================

This is critical.

Implement V1A behind a server-readable feature flag or league allowlist.

The flag must control PRESENTATION ONLY.

When Swayger Run is OFF:

- render the existing current Weekly all-cards experience
- preserve all saved picks
- preserve autosave
- preserve editing
- preserve guest/auth identity
- preserve Call Your Shot
- preserve League Picks
- preserve settlement
- preserve results
- preserve receipts
- preserve analytics compatibility

When Swayger Run is ON:

- render the new focused Swayger Run experience

Turning the flag OFF must require:

NO migration rollback
NO data migration
NO cleanup job
NO pick conversion
NO participant conversion

Rollback goal:

One configuration change should return a pilot league to the current Weekly play UX.

Document exactly:

- where the flag lives
- how it is enabled for a league
- how it is disabled
- whether app redeploy is required
- what remains persisted when disabled

For initial rollout:

Enable for internal/test league first.

Then make Food Pyramid XX eligible after manual internal QA.

Do not globally enable by default.

==================================================
4. PRESERVE EXISTING SAVE ARCHITECTURE
==================================================

Do NOT rewrite the pick-saving system.

Preserve:

- optimistic answer selection
- serialized per-prop saves
- server-confirmed baseline
- rollback on failed save
- current autosave endpoint
- answer-universe validation
- guest/auth participant architecture

The new UX must sit on top of this existing machinery.

All progress and completion behavior must be based on SERVER-CONFIRMED state.

Never treat an optimistic answer as completed for:

- progress meter
- auto-advance
- completion
- haptics
- acknowledgement

==================================================
5. ONE-CARD FOCUS MODE
==================================================

When Swayger Run is enabled:

Show one Swayger Moment as the primary focused card at a time.

Concept:

BASEMENT WATCH

[Answer selector]

Navigation:

- Previous / Back
- Next where appropriate
- interactive meter segments
- Review Picks after completion

Do NOT add swipe gestures.

Use stable prop IDs for active Moment state.

Do not rely only on array indexes for delayed-save behavior.

==================================================
6. INITIAL / RESUME BEHAVIOR
==================================================

Resolve the initial focused Moment only AFTER server-confirmed picks have hydrated.

New participant:
open the first Moment.

Returning incomplete participant:
open the first unanswered confirmed Moment.

Examples:

2 of 5 completed:
open first unanswered.

4 of 7 completed:
open first unanswered, regardless of numeric position.

If Moment 2 previously failed to save:
resume at Moment 2.

Returning completed participant:
open directly into the completion summary.

Do not:

- briefly show Moment 1 before hydration
- persist a separate resume index
- force completed participants through all Moments again

The server-confirmed pick state is the source of truth.

7. SWAYGER METER
==================================================

Implement the recommended segmented horizontal progress track.

Concept:

YOUR SWAYGER

● ● ◉ ○ ○

2 of 5 calls made

States:

- completed
- current
- unanswered
- saving
- error

Requirements:

- support at least 3–12 Moments
- do not hardcode five
- compact on mobile
- responsive on web
- segments contract rather than wrap for larger counts
- each segment may navigate to its Moment
- meter cannot be the only progress indicator

Always show accessible text:

Moment N of Y

Do not build:

- custom S-shaped path
- curved SVG
- canvas
- physics
- decorative animation loop

==================================================
8. ANSWER SELECTION + SAVING STATE
==================================================

Preserve existing AnswerSelector behavior.

After a user selects an answer:

1. Optimistic selected state may appear as today.
2. Show a clear saving state.
3. Do NOT advance yet.
4. Wait for successful server confirmation.
5. On confirmation:
   - convert to confirmed visual state
   - update Swayger meter
   - show acknowledgment
   - fire haptic where supported
6. On failure:
   - restore previous confirmed answer
   - show existing/error feedback
   - do not advance
   - do not fire success haptic

Concept:

Saving your call…

then:

SELECTED

All Eyez On Me

ON THE RECORD ✓

==================================================
9. ACKNOWLEDGMENT MICROINTERACTION
==================================================

Use a small deterministic acknowledgement system.

Do not randomize copy on rerender.

Recommended copy:

New confirmed answer:
ON THE RECORD

Edit of existing confirmed answer:
CALL UPDATED

Final required confirmed answer:
YOUR SWAYGER IS IN

Do not use RECEIPT PENDING on every answer.

Use RECEIPT PENDING only in completion state.

Visual treatment should be subtle:

- stronger selected state
- checkmark fade-in
- small border/background emphasis
- optional scale from approximately 0.99 → 1.0
- progress segment fills
- no confetti
- no card flips
- no looping glow

Respect reduced-motion preference.

==================================================
10. AUTO-ADVANCE
==================================================

After a NEW previously unanswered pick is successfully confirmed:

show acknowledgement for approximately 500–700ms

then advance to the next unanswered Moment.

Do not auto-advance:

- while saving
- after error
- when editing a previously confirmed answer
- after final required answer
- if participant manually navigated away before save completed
- when reduced-motion handling indicates immediate/static transition is preferable

Use stable prop identity so a delayed response cannot advance the wrong Moment.

==================================================
11. EDITING
==================================================

Before lock:

Users must remain able to review and edit completed Moments.

Navigation:

- Previous
- Next
- meter segment
- Review Picks
- Edit Picks from completion summary

Changing an already-confirmed answer:

- preserve overall completion
- preserve filled progress segment
- show `CALL UPDATED` after successful confirmation
- do not replay the main completion payoff
- do not replay the final-completion haptic
- do not auto-advance solely because of an edit

After lock:

- play experience becomes read-only per existing rules
- meter/navigation may still support review
- no edits
- League Picks behavior unchanged

==================================================
12. HAPTICS
==================================================

`expo-haptics` is already installed.

Use it carefully.

Successful normal pick save:

`Haptics.impactAsync(ImpactFeedbackStyle.Light)`

Final required pick:

`Haptics.notificationAsync(NotificationFeedbackType.Success)`

Rules:

- only after successful server confirmation
- never on optimistic selection
- never on restored saved picks at load
- never on failed save
- gracefully no-op on web
- catch failures
- haptics can never break the save flow
- visible feedback must always exist independently

Do not add sound.
