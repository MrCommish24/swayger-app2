# Swayger Global Game Day Settlement System

Build a safe, scalable global settlement system for Swayger Game Day Rooms.

The goal is to allow an authorized administrator or global Game Day operator to settle the same real-world prop once across multiple rooms, while preserving the existing ability for each room host to settle props individually from the current host panel.

This is an additive feature.

The existing room-level settlement workflow must remain fully functional and unchanged.

---

# Core product requirement

Swayger must support two parallel settlement options:

## Option 1: Existing room-level settlement

A host can continue opening an individual Game Day Room and settling each prop manually from that room’s host panel.

This workflow must remain available.

Do not remove, replace, simplify, redirect, or materially change it.

## Option 2: New global settlement

An authorized global operator can view locked, unsettled props across multiple active rooms and settle equivalent real-world props in bulk.

The operator should answer one real-world question once and apply that result safely to every matching room prop.

Example:

If 12 rooms contain the exact same real-world prop for the same game:

“Which team scores first: Knicks or Celtics?”

The global operator should be able to select the correct team once and settle all 12 matching room props.

However, props must only be grouped when they truly represent the same real-world question.

---

# Critical safety principle

Do not group props using only:

- `template_prop_id`
- Rendered question text
- Answer-option position
- `TEAM_A` or `TEAM_B` placeholder position
- Template name alone

Those fields are not sufficient to prove that two props should share the same settlement.

The same template can render different questions:

- LeBron vs. Tatum
- Curry vs. Luka

The same generic question text can appear in different games:

- “Who scores first?”
- “Will the home team score next?”
- “Which star finishes with more points?”

Team A and Team B can also be reversed between rooms.

The system must establish that props belong to:

1. The same sporting event
2. The same phase or settlement context
3. The same real-world prop definition
4. The same underlying teams, players, threshold, or entities
5. A compatible answer schema

Only then may they be bulk settled.

# Authorization model

Use the safest role model supported by the current application.

## Room hosts

Room hosts must continue settling props individually inside rooms they are authorized to manage.

Do not give ordinary hosts global access to other hosts’ rooms.

If host-level bulk settlement is supported, it must be scoped only to rooms that host owns or is explicitly authorized to manage.

## Global operator or administrator

Bulk settlement across all active rooms should only be available to:

- Existing admins
- Or a clearly defined global Game Day operator role

Do not infer global authorization merely because a user can host one room.

Do not expose the global settlement queue to ordinary participants.

All write endpoints must enforce authorization on the server.

Client-side hiding is not sufficient.

---

# Preferred long-term grouping model

The durable solution should use a canonical settlement identity.

Conceptually, equivalent props should share a settlement signature derived from:

- Event identity
- Canonical prop definition
- Phase
- Resolved entities
- Threshold or line, when applicable
- Answer schema
- Prop/template version

Example:

`event_key + canonical_prop_key + phase + entity_bindings + answer_schema_version`

Possible examples:

`NBA_2026_LAL_BOS_2026-11-18 + PLAYER_MORE_POINTS + LEBRON_JAMES|JAYSON_TATUM + PREGAME + PLAYER_CHOICE_V1`

`NFL_2026_CHI_GB_2026-09-13 + FIRST_TEAM_TO_SCORE + CHI|GB + PREGAME + TEAM_CHOICE_V1`

The exact implementation must be based on the current schema.

Do not invent external IDs that the application does not currently have.

---

# Safe Phase 1 grouping fallback

If the current schema does not support a complete canonical settlement key yet, build a safe transitional signature using the strongest current data available.

At minimum, the grouping signature should include:

- Stable game or event identity
- Phase or pick-card type
- Normalized rendered question
- Normalized answer schema
- Resolved team/player identities or names
- Threshold or line value, if applicable
- Template version or template ID as an additional signal

A transitional signature might resemble:

`normalized_event_key + phase + normalized_question + normalized_answer_schema + normalized_entities`

Do not use question text by itself.

Do not use template ID by itself.

If the application cannot reliably establish event identity or entity equivalence, stop and report the limitation before enabling bulk settlement.

# Event grouping in the interface

The global settlement queue should be organized first by sporting event.

Example:

## Knicks vs. Celtics
November 18, 2026

### Pregame
- Which team scores first? — 12 rooms
- Jalen Brunson or Jayson Tatum: more points? — 8 rooms
- Total points over 221.5? — 6 rooms

### Halftime
- Which team wins the third quarter? — 10 rooms
- Will the game be within 5 points entering the fourth? — 7 rooms

Do not show one undifferentiated list of every question across every game.

Recommended hierarchy:

1. Sport or league
2. Game/event
3. Phase
4. Unique settlement group
5. Included rooms and props

# Global settlement queue

Create a read endpoint for the global queue.

A possible route is:

`GET /api/admin/gameday/settlement-queue`

Use current routing conventions if a better route already exists.

The queue should return only props that are:

- In rooms eligible for settlement
- On locked pick cards
- Not already settled
- Associated with active, live, finalizing, or otherwise valid room statuses
- Within the authorized user’s settlement scope

Do not include:

- Draft rooms
- Archived rooms unless explicitly requested
- Open cards
- Closed but not locked cards if settlement is not currently allowed
- Already settled props
- Deleted or invalid props
- Props from rooms the operator is not authorized to manage

# Conflict detection

The backend must detect and block unsafe groups.

A settlement group must not be bulk-settleable when:

- Props belong to different games
- Phases do not match
- Questions appear similar but entity bindings differ
- Thresholds differ
- Answer schemas differ
- One prop uses Yes/No and another uses Team A/Team B
- Answer labels match but stable values do not
- One room has reversed team mappings that cannot be safely resolved
- One prop is already settled
- One pick card is not locked
- One room is not eligible
- The group changed after the operator loaded the queue
- Any included prop cannot map the selected answer safely

Blocked groups may still appear in the interface as an exception requiring individual room settlement.

Do not silently split or merge ambiguous props without making the reason visible.

---

# Answer-option mapping

Never apply an answer by array position.

Do not assume:

- Option 0 means Team A
- Option 1 means Team B
- First displayed answer is equivalent across rooms

Bulk settlement must map the selected real-world answer to each prop using a stable value or normalized entity identity.

Example:

The operator selects:

`Boston Celtics`

Room A may store options:

- Boston Celtics
- New York Knicks

Room B may store:

- New York Knicks
- Boston Celtics

Both can still be settled safely if the backend maps by stable team identity or normalized value.

If mapping cannot be proven, block bulk settlement for that group.

# Global settlement write endpoint

Create a separate server endpoint for the write operation.

A possible route is:

`POST /api/admin/gameday/settle-group`

Use current route conventions where appropriate.

The request should include:

- `group_key`
- Selected answer key or canonical answer value
- Expected prop IDs
- Expected prop count
- Optional client-generated idempotency key
- Optional operator note

Do not allow the client to send only question text and request that every matching row be updated.

The backend must settle an explicitly reviewed set of prop IDs.

---

# Required server-side revalidation

Before applying a global settlement, the server must revalidate every included prop.

Confirm:

- Operator is authorized
- Prop still exists
- Room is still eligible
- Card is still locked
- Prop is still unsettled
- Prop still belongs to the requested event
- Prop still belongs to the settlement group
- Selected answer is valid
- Selected answer maps safely to that prop
- Expected prop set or count still matches
- No conflicting update occurred since preview

If the queue changed, do not automatically include new props.

Return a message such as:

“Settlement group changed. Refresh and review before continuing.”

---

# Idempotency

Global settlement must be idempotent.

Repeated submission of the same request must not:

- Award points twice
- Rescore the same picks twice
- Duplicate transactions
- Duplicate audit records incorrectly
- Produce inconsistent room totals

Use the current room-level settlement protections if they already exist.

If those protections are not sufficient, add a safe idempotency mechanism.

Do not weaken the existing individual settlement path.

---

# Transaction and scoring requirements

Use the existing room-level settlement logic as the single source of truth whenever possible.

Do not create a second independent scoring implementation that could diverge.

The global settlement endpoint should preferably:

1. Validate the group
2. Invoke the same underlying settlement/scoring function for each prop
3. Capture success or failure for each prop
4. Recalculate or refresh affected room leaderboards through the existing mechanism
5. Return a detailed result summary

If the current settlement logic cannot be safely reused, refactor it into a shared server-side helper used by both:

- Individual room settlement
- Global group settlement

Do not duplicate point-award calculations in two places.

---

# Atomicity and partial failure

Inspect whether a single database transaction across all affected rooms is practical and safe.

Preferred behavior:

- A settlement group is applied atomically when feasible
- Either all eligible props settle or none do

If true cross-room atomicity is not feasible with the current architecture, implement explicit partial-failure handling.

The response must identify:

- Props successfully settled
- Props skipped because they were already settled
- Props that failed
- Rooms affected
- Error reason for each failure
- Whether a retry is safe

Do not return only a generic success message when some props failed.

- Operator user ID

- Timestamp
- Group key
- Event key
- Question

- Affected prop IDs
- Affected room IDs
- Expected count

If an audit table already exists, reuse it.

If not, propose the smallest suitable audit structure.

Do not log secrets, admin tokens, or participant private information.

# Corrections and overrides

Preserve the existing ability to correct an individual room prop if a global result was wrong or one room was configured differently.

The system should make it visible that a prop was settled through global settlement.

If the current application supports reversing or correcting settlement, keep using that workflow.

If corrections are not currently supported, do not invent an unsafe automatic reversal system.

Instead:

- Clearly document the limitation
- Add audit visibility
- Preserve individual room controls
- Require explicit confirmation for any future correction feature

# Legacy and historical-room compatibility

The global queue must handle older rooms safely.

Older props may lack:

- Stable event IDs
- Structured entities
- Versioned templates
- Stable answer keys

For legacy props:

- Use the safe transitional signature only when equivalence can be proven
- Otherwise mark them as requiring individual settlement
- Never force them into a bulk group based solely on text similarity

It is acceptable for some legacy props to remain manual.

Safety is more important than grouping every prop.

# Testing requirements

Create tests for at least the following scenarios.

## Correct grouping

- Same event, same question, same entities, same options
- Same event, same template, different player matchup
- Same event, same question, reversed option order
- Same event, same question, different phase
- Same event, same question, different threshold
- Different events, identical rendered question
- Different sports, identical rendered question
- Same event, minor capitalization or whitespace differences
- Legacy room with missing structured identity

## Settlement safety

- All props settle successfully
- One prop already settled before confirmation
- One card reopened after preview
- One room archived after preview
- Group count changes between preview and submit
- Operator submits twice
- Selected answer is missing from one prop
- Answer options reversed in one room
- Scoring fails for one prop
- Leaderboards refresh correctly
- Individual host settlement still works afterward

## Authorization

- Normal participant cannot load queue
- Normal host cannot access other hosts’ rooms
- Authorized admin can access all eligible rooms
- Host-scoped global settlement, if supported, includes only owned rooms
- Missing or invalid admin token is rejected server-side

## UI

- No eligible props
- One event
- Multiple events
- 50+ groups
- Conflict group
- Partially failed group
- Mobile web
- Desktop web
- Long question text
- Long team/player names
- Large room counts

# Performance requirements

The system should scale to at least:

- 20 active rooms
- 500 locked props
- 50–100 unique settlement groups

Avoid:

- One database request per prop during queue loading
- N+1 room queries
- Sending unnecessary pick-level participant data to the client
- Recalculating unaffected rooms
- Rendering hundreds of expanded rows by default

Use grouped queries and collapsed UI sections where possible.

Do not prematurely optimize beyond the current architecture, but avoid obvious scaling problems.
