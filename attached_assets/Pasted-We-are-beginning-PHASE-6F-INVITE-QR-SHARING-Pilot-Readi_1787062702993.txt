# PHASE 6F — INVITE & QR SHARING
## Pilot Readiness Convenience Pass

Phase 6A–6E are complete.

Current Phase 6 product:

- bulk league import
- 10–16 member roster UX
- post-lock League Picks / receipts
- weekly reward flexibility
- safe archive / restore
- repeatable weekly commissioner workflow
- guest/account joining
- guest recovery
- commissioner-assisted recovery

We are preparing for a real-world Fantasy pilot later this week.

The goal of 6F is:

# MAKE IT EXTREMELY EASY FOR A COMMISSIONER TO GET 10–15 PEOPLE INTO SWAYGER IN PERSON.

The primary use case is Draft Day / league setup:

Commissioner is in a room with league members.

Instead of texting the invite URL individually, commissioner opens:

Invite Your League

→ displays QR code

→ members scan

→ existing Fantasy join flow opens

We also want:

- native Share Invite
- Copy Link

Do NOT create another invitation identity system.

==================================================
3. PRIMARY PRODUCT RULE
==================================================

THE QR CODE IS JUST ANOTHER REPRESENTATION OF THE EXISTING CANONICAL INVITE URL.

It must NOT contain:

- guest_token
- recovery token
- user_id
- league_member_id
- season_member_id
- fantasy_team_id
- claim ID
- authentication credentials

Scanning the QR should be security-equivalent to receiving the normal league invite link.

==================================================
4. CANONICAL INVITE URL
==================================================

Find and reuse the existing Fantasy league join URL.

Conceptually it may look like:

/fantasy/join/:leagueId/:seasonId

or whatever the actual current route is.

Do not guess.

Use one helper so:

QR
Share Invite
Copy Link

all use EXACTLY the same canonical URL.

Preferred helper concept:

buildFantasyInviteUrl(leagueId, seasonId)

If one already exists:
reuse it.

==================================================
5. FULL HTTPS URL
==================================================

The QR must encode a real externally usable HTTPS URL.

Do not encode only an Expo Router pathname such as:

/fantasy/join/abc

unless the QR library/browser flow already resolves that correctly.

Use the app's established public web origin.

Example conceptually:

https://<swayger-domain>/fantasy/join/...

Inspect existing share-link generation and use the same origin strategy.

Do not hardcode a development Replit URL if production URL configuration already exists.

==================================================
6. QR DEPENDENCY AUDIT
==================================================

Before adding a package, inspect package.json.

If the project already has a QR library:
reuse it.

If not:

choose a lightweight maintained React Native / Expo-compatible QR component.

Examples of acceptable architecture:

react-native-qrcode-svg

or an equivalent already-compatible package.

Do not add a large dependency.

Do not create QR codes on the backend.

QR generation should be client-side from the canonical URL.

8. QR SIZE
==================================================

QR should be large enough to scan easily from:

- another phone
- across a draft table
- laptop screen
- TV/tablet if commissioner mirrors it

Aim around:

220–280 px logical size

depending on viewport.

Do not render a tiny QR inside a card.

==================================================
9. QR CONTRAST
==================================================

High scanning reliability matters more than decorative styling.

Use:

dark QR
light background
clear quiet zone

Do NOT:

- put complex gradients through QR modules
- distort modules
- put busy imagery behind it
- over-brand the QR

If adding Swayger logo to center:
ONLY do so if the QR package/error correction supports it and scanning remains reliable.

For V1:
plain QR is acceptable and probably preferable.
