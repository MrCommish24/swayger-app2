# PHASE 5.2 — REPEATABLE FANTASY SEASON / WEEK 2+

Current verified state:

- Draft Day works
- Week 1 Swayger works end-to-end
- existing members/guests return without rejoining
- weekly share + reminder + Copy Link work
- participation counts work
- Week 1 settlement/finalization works
- Season Standings aggregate Draft Day + Week 1
- weekly routes already use :weekNumber
- buildWeekUrl(leagueId, seasonId, weekNumber) is generic
- Phase 5 and 5.1 regressions are green

The next goal is NOT to build 18 hardcoded weeks.

The goal is to make the weekly operating loop repeatable:

Week N finalizes
→ commissioner creates Week N+1
→ league members automatically have access
→ same share/re-engagement flow
→ same settlement flow
→ Season Standings accumulate

==================================================
1. PRODUCT PRINCIPLE
==================================================

Fantasy Season should feel like one persistent league.

The commissioner should NOT:

- recreate the league
- re-add members
- resend a league join invitation
- rebuild identity
- configure a completely new system every week

Members should NOT:

- reclaim a seat
- rejoin
- select their team again
- create another account

Each new week is simply the next Swayger inside the existing Fantasy season.

5. CURRENT / NEXT WEEK MODEL
==================================================

We need a simple way for the hub to know:

- latest published weekly competition
- next week available to create

Do NOT use today's NFL calendar yet.

V1 should derive from existing Swayger data.

Suggested logic:

published weekly rooms sorted by week_number ASC.

current/latest week =
highest existing week_number

next week =
if no weekly rooms exist → 1
else highest week_number + 1

Examples:

No weekly room:
next = Week 1

Week 1 exists:
current = Week 1
next = Week 2

Week 1 + Week 2 exist:
current = Week 2
next = Week 3

Do not infer from real NFL schedule.

==================================================
6. SHOULD NEXT WEEK BE CREATABLE BEFORE CURRENT WEEK FINALIZES?
==================================================

Product rule for V1:

Prefer requiring the previous weekly Swayger to be FINALIZED before commissioner can create the next one.

Example:

Week 1 open/locked/resolving:
do NOT offer Set Up Week 2 yet.

Week 1 finalized:
offer:

Set Up Week 2

This keeps the operating model simple and avoids overlapping weekly Swaygers in V1.

Enforce server-side, not just UI.

If there is a strong architectural reason not to enforce this, report it before changing the rule.
