We are implementing the next focused refinement to Swayger Fantasy Weekly.

# SWAYGER RUN V1C — PICK SHARE PACKAGING

Context:

Swayger Run V1B.1 is complete.

Current Weekly Fantasy sharing now supports:

- Share Pick before lock
- Share Pick after lock
- persisted My Lock
- Share My Lock before/after lock
- one-pick-only disclosure
- protected Weekly destination
- source attribution
- existing analytics
- Swayger Moment-specific share copy

Manual GroupMe QA surfaced a presentation problem:

The actual shared take is strong, but the canonical Weekly URL is extremely long and visually noisy.

Example current share:

SCOREBOARD KING

Mr Roarke has Big Guns putting up the highest fantasy score this week.

Swayger Fantasy • Food Pyramid XX • Week 2
Who you got?
https://www.swayger.app/fantasy/weeks/<leagueId>/<seasonId>/2/play?source=pick_share

GroupMe then also renders the generic Swayger marketing preview card.

This creates too much vertical noise.

V1C goal:

MAKE A SHARED PICK FEEL LIKE A CLEAN SOCIAL OBJECT.

Product principles:

SHORT LINK.
COMPACT COPY.
PICK-SPECIFIC PREVIEW.
SAME PROTECTED DESTINATION.
NO EXPANSION OF PUBLIC PICK ACCESS.

==================================================
2. SHARE URL GOAL
==================================================

Replace the long visible canonical Weekly URL in shared-pick output with a short Swayger URL.

Preferred shape:

https://www.swayger.app/p/<shortCode>

or equivalent compact dedicated namespace.

Preferred displayed form where reliable:

swayger.app/p/<shortCode>

The short URL should resolve to the same Weekly participation destination and preserve:

source=pick_share

Human flow:

short link
→ protected Weekly play/join route
→ existing auth/guest/lock handling

Do NOT redirect to:

- homepage
- generic marketing
- receipt
- public pick detail page

The short link is a routing/preview layer only.

==================================================
3. SHORT-LINK DATA MODEL
==================================================

Audit whether an existing generic short-link table/helper can safely support this.

Do NOT reuse receipt aliases in a way that mixes finalized receipt semantics with live pick-share semantics.

If a dedicated additive table is required, use the smallest safe model.

Conceptually:

fantasy_pick_share_aliases

Potential fields:

- short_code
- room_id
- participant_id
- prop_id
- created_at
- optional created share context only if truly necessary

Important:

Do NOT store:
- answer label
- team name
- generated share text
- email
- phone
- guest token
- auth token

The current answer should be resolved from the participant’s confirmed pick where safe.

However, think carefully about whether a previously shared pick should remain tied to the answer that was intentionally disclosed at share time if the user later changes that pick before lock.

This is a product decision.

Assess and recommend one of:

A. Snapshot the intentionally shared answer at share time.
B. Resolve the participant’s current confirmed answer dynamically.

Strong product preference:

A shared message should not silently change meaning later.

So if the alias needs to preserve the deliberately shared answer identity, store the minimum stable answer identifier necessary rather than raw display text.

If schema is required:
prepare the migration and STOP with:

SQL APPLICATION REQUIRED

before dependent implementation.

==================================================
4. STABILITY / ALIAS SEMANTICS
==================================================

We need deterministic, understandable behavior.

Assess whether:

- one alias should exist per participant + prop + shared answer
- repeated shares of the same current pick should reuse one alias
- changing the pick should generate a new alias
- My Lock sharing and ordinary Share Pick should reuse the same alias when they refer to the same participant/prop/answer

Preferred behavior:

Same participant
+ same Weekly room
+ same prop
+ same confirmed answer

→ stable reusable alias

If the participant changes the pick:

→ old alias continues representing the old voluntarily shared call
→ new share gets a new alias

This prevents previously sent links/previews from changing meaning.

Do not create unbounded duplicate aliases for repeated sharing of the same exact call.

==================================================
5. SHORT CODE
==================================================

Use the project’s existing secure short-code convention if appropriate.

Requirements:

- globally unique
- opaque
- not sequential
- not guessable from IDs
- no private data encoded
- compact enough for messaging
- collision-safe

Do not put league ID, participant ID, prop ID, answer ID, or week number in the URL.

Example:

→ 302

Preserve existing:

- auth
- guest claim
- seat identity
- locked state
- League Picks gating
- archived/finalized routing
- source attribution

The alias itself must not grant protected Weekly access.

==================================================
11. PRE-LOCK EDIT BEHAVIOR
==================================================

Important edge case:

A participant may share a pick and then change it before lock.

V1C must define historical short-link behavior clearly.

Preferred rule:

A previously shared alias remains a receipt of what the participant intentionally shared at that moment.

Changing a pick later does NOT mutate:
- previously generated preview metadata
- previously sent link meaning

Future share after changing the pick:
- generates/reuses alias for the new confirmed answer

This is consistent with the Swayger ethos:
the old take remains on the record.

Do not attempt to edit previously sent messages.

==================================================
12. MY LOCK CHANGE BEHAVIOR
==================================================

If a participant:

1. Shares My Lock
2. Changes My Lock before lock
3. Shares the new My Lock

Then:

- old alias remains associated with the old shared call
- new My Lock share reflects the new selected Lock
- old preview should not silently become “not My Lock” or change content

If necessary, share context should snapshot whether the alias was created as:

- normal pick share
- My Lock share

Use the minimum data required.

16. PRIVACY / SECURITY
==================================================

Public preview metadata is allowed only because the participant intentionally shared that exact pick.

The alias must not be usable to enumerate other picks.

Requirements:

- opaque short codes
- no sequential IDs
- no directory/index endpoint
- no public search
- no participant profile
- no “more picks from this user”
- no other Week data
- no League Picks data
- no protected API access

Malformed, unknown, revoked/invalid aliases:
return safe 404.

If underlying Week is deleted:
alias should fail safely.

If participant or prop no longer exists:
fail safely.
