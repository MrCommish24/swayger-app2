We are live-testing Pick Card Creator V2 and found a confirmed participant-web blocker.

DO NOT redesign Pick Card architecture.

The V2 backend is already creating the bonus_total prop correctly.

LIVE EVIDENCE

The participant card shows:

- 3 main matchup props
- 1 Bonus Game prop
- "Total points in the Bonus Game?"
- 4/5 answered

However, under:

"Total points in the Bonus Game?"

there is NO input control.

The participant therefore cannot answer the fifth required prop and cannot lock picks.

This means the participant Game Day UI is not rendering V2 integer props.

==================================================
GOAL
==================================================

Add participant-side support for:

answer_type = "integer"

specifically the current:

prop_role = "bonus_total"

Do not create another backend representation.

Use the existing backend contract.

==================================================
CURRENT BACKEND CONTRACT
==================================================

Integer prop example:

{
  "prop_role": "bonus_total",
  "answer_type": "integer",
  "question": "Total points in the Bonus Game?",
  "numeric_min": 0,
  "numeric_max": 200,
  "answer_options": []
}

Participant write:

POST /api/gameday/props/:propId/pick

{
  "numeric_answer": 54
}

Backend requires:
- JSON number
- integer
- min 0
- max 200

Saved participant response provides:

my_pick_details[propId] = {
  "selected_answer": "54",
  "numeric_answer": 54
}

numeric_answer is authoritative.

==================================================
PARTICIPANT UI
==================================================

For:

answer_type === "integer"

render a numeric input directly underneath the prop question.

Example:

Total points in the Bonus Game?

[ 54 ]

Requirements:

- inputmode="numeric" or appropriate numeric mobile input
- whole number only
- respect numeric_min / numeric_max
- display 0–200 validation clearly
- persist existing saved numeric_answer when returning to the card
- changing the value before lock updates the pick using existing pick endpoint
- do not use answer_options
- do not convert this into dozens/hundreds of buttons
- do not treat numeric strings as the backend payload

The request must send:

{
  "numeric_answer": Number(value)
}

after client validation.

==================================================
COMPLETION LOGIC
==================================================

The current card correctly knows this is the fifth required prop.

Make sure the UI considers an integer prop answered when it has a valid saved numeric_answer.

Important edge case:

0 is a valid answer.

Do NOT use truthiness such as:

if (numeric_answer)

because 0 would incorrectly count as unanswered.

Use explicit null/undefined checks.
