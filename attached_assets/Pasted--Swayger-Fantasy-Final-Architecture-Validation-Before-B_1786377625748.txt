# Swayger Fantasy — Final Architecture Validation Before Build Authorization

Do not write code, apply migrations, or modify any files yet.

We have reviewed your full Swayger Fantasy pre-build architecture assessment and agree with the overall direction:

* persistent `fantasy_leagues`
* persistent league membership
* Draft Day as the first competition inside the league
* reuse of `gameday_rooms` as the competition/event layer
* reuse of existing cards, props, picks, settlement, leaderboard, and finalization
* separation of `sport`, `experience_type`, and `competition_type`
* support for Draft Day competition-scoped props and season-long props
* sports-agnostic architecture
* future manual/API import compatibility
* no payment custody or fantasy-platform API integration in the first release

Before implementation is authorized, perform one final architecture review focused ONLY on the unresolved structural questions below.

The objective is to ensure we are not creating technical debt that immediately appears when Week 1 is built after Draft Day.

---

# 1. Reassess `fantasy_season_scores`

Your current recommendation creates:

`fantasy_season_scores`

with persisted cumulative point totals.

We need to determine whether this should actually be the source of truth.

The concern is synchronization and double-counting.

Examples:

* a commissioner settles a prop incorrectly
* Swayger admin corrects the result
* a settled prop is re-settled
* an event result is recalculated
* a competition is reopened
* a season-long prop settles months after Draft Day
* a member's result is corrected after finalization

If season totals are incrementally written, we need confidence they cannot drift away from underlying picks/results.

Compare at least these approaches:

### Option A — Persisted cumulative standings

`fantasy_season_scores` is updated whenever qualifying points are earned or reversed.

### Option B — Derived standings

Season standings are calculated from underlying settled props/picks across all competitions belonging to the league.

### Option C — Hybrid

Underlying competition/pick results remain the authoritative source, while a cached/materialized season score is maintained for performance.

Recommend one.

For your recommendation explain:

* authoritative source of truth
* how corrections work
* how re-settlement works
* how double-counting is prevented
* whether finalization is required before points count
* how season-long Draft Day props eventually count
* whether historical standings can be reconstructed from source records
* expected query/performance impact for a normal 8–14 member fantasy league over a season

We strongly prefer correctness and auditability over premature optimization.

# 2. Reassess whether `fantasy_teams` should be first-class NOW

Your current recommendation stores:

`team_name`

directly on `fantasy_league_members` for MVP, with a possible separate `fantasy_teams` table later.

Week 1 is an immediate fast follow.

Weekly Swayger props will frequently concern the fantasy team itself.

Examples:

* Which fantasy team scores the most points this week?
* Which team wins by the largest margin?
* Which team leaves the most points on the bench?
* Which fantasy team finishes first in regular-season scoring?

We need to know whether storing `team_name` on the member row creates immediate rework.

Compare:

### Option A

Keep `team_name` on `fantasy_league_members`.

### Option B

Create a first-class `fantasy_teams` table now.

If recommending Option B, consider a structure conceptually like:

Fantasy League
→ Fantasy Team
→ current manager/member

but do not implement this exact model automatically.

Address:

* team identity versus manager identity
* team name changes
* team ownership changes
* co-managers
* future platform imports
* weekly team-target props
* historical results
* whether a fantasy team should survive a manager replacement

Recommend the smallest architecture that does NOT need immediate restructuring for Week 1.

# 3. Stable answer-option identity

Current Game Day props use `answer_options` as plain text arrays.

Your proposal adds:

`answer_target_type`

Examples:

* league_member
* fantasy_team
* player
* text
* yes_no

However, `answer_target_type` alone does not establish which persistent object an answer represents.

Example:

Question:
Who drafts the first QB?

Display answer:
Darius

But ideally the underlying target may be:

`fantasy_league_member_id = abc123`

Similarly:

Question:
Which fantasy team scores the most?

Display answer:
The Monstars

Underlying target may be:

`fantasy_team_id = xyz789`

Assess whether Fantasy should continue storing only strings or whether answer options need stable IDs underneath their labels.

Compare:

### Option A — Strings only

`["Darius","Chris","Mike"]`

### Option B — Structured answer options

Conceptually:

```json
[
  {
    "id": "member-uuid",
    "label": "Darius",
    "type": "league_member"
  }
]
```

### Option C — Existing display strings plus separate option-target metadata

Recommend the minimum clean solution.

Address:

* renaming a league member
* renaming a fantasy team
* commissioner correcting a typo
* historical receipts
* settlement
* existing Game Day compatibility
* global settlement compatibility
* future fantasy-platform imports
* manually entered NFL/fantasy players
* yes/no and static text options

Do not overengineer this, but we do not want Fantasy results tied forever to fragile display strings if stable entity references are required.

# 4. Identity claiming across leagues and devices

Your current proposal stores:

`guest_session_id`

on `fantasy_league_members`, with a uniqueness constraint.

Reassess this carefully.

Potential scenarios:

* the same person participates in two different Swayger Fantasy leagues
* the same guest device belongs to someone participating in multiple leagues
* a user joins Draft Day on their phone and Week 1 on their laptop
* a guest later creates an authenticated Swayger account
* a member replaces their phone
* a family shares a device
* a commissioner needs to reset an incorrect claim

We need identity claiming to be persistent enough to eliminate weekly re-onboarding without making a single browser session the permanent identity system.

Recommend the correct relationship between:

* Swayger user
* guest/device session
* fantasy league member
* competition participant

Consider whether identity claims need their own table rather than storing one session value directly on the member.

For example conceptually:

`fantasy_member_claims`

Do not assume that is necessary; assess it.

Explain:

* what uniquely identifies the member
* what identifies the device/session
* whether multiple claims/devices can point to the same league member
* how authenticated accounts supersede or coexist with guest claims
* how a commissioner/admin resets a bad claim
* how duplicate claims are prevented
* how Week 1 recognizes an existing member

Keep Draft Day onboarding simple.

# 5. Preserve historical identity and ownership

Your assessment currently suggests a commissioner can update:

* display name
* team name

on `fantasy_league_members`

for replacement or ownership changes.

We need to make sure historical Swayger receipts do not change retroactively.

Example:

Weeks 1–6:

Mike manages **The Monstars**

Week 7:

Chris takes over **The Monstars**

Historical Week 2 results should still correctly communicate who made those picks and who managed the team at the time.

Assess:

* which fields can safely be edited
* which historical values should be snapshotted on competition participation/results
* whether team ownership needs effective dates
* whether a manager replacement should create a new league-member record
* whether a fantasy team should remain the same team while ownership changes

We do not need a sophisticated franchise-history feature.

We DO need to avoid mutating historical receipts accidentally.

Recommend the smallest safe model.
