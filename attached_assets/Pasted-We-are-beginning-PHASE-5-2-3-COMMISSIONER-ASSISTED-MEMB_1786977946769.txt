==================================================
1. REAL USER PROBLEM
==================================================

A Fantasy member originally joins as a guest.

Example:

Rob
Team: Grim

That creates a persistent Fantasy identity with:

- fantasy_league_member
- fantasy_season_member
- fantasy_team relationship
- historical Draft Day picks
- weekly picks
- standings history
- active fantasy_member_claim tied to a guest_token stored on the original browser/device

Later Rob:

- loses the device
- clears browser storage
- used incognito/private browsing
- otherwise loses the original guest token

The database still knows Rob's seat is claimed.

But Rob can no longer prove ownership because the only credential was the lost guest token.

Rob contacts the commissioner:

"How do I get back into Swayger?"

Today the commissioner has no safe recovery mechanism.

We need:

# SINGLE-USE COMMISSIONER RECOVERY LINK

The commissioner authorizes recovery of Rob's EXISTING Fantasy identity.

Rob receives a private recovery link.

Rob MUST authenticate/create a Swayger account.

After successful authenticated redemption:

that account takes ownership of Rob's existing Fantasy member claim.

Everything else remains the same.

==================================================
2. SECURITY PRINCIPLE — NON-NEGOTIABLE
==================================================

The recovery URL itself is NOT authentication.

It only authorizes:

"This specific Fantasy member identity is permitted to be recovered."

It must NOT mean:

"The person holding this URL is automatically Rob."

The person opening the recovery link MUST:

- Sign In
or
- Create Account / complete normal authentication

before ownership is transferred.

Do NOT allow anonymous recovery redemption.

==================================================

- fantasy_league_member.id

- fantasy_team relationship
- gameday_participant history
- Draft Day picks
- weekly picks

- weekly results

- competition participation history

- delete Rob

- recreate Rob

- reset competition participation
- trigger open-roster behavior

Only identity ownership changes.

6. RECOVERY TOKEN MODEL
==================================================

We likely need a durable server-side recovery record.

Preferred conceptual table:

fantasy_member_recovery_tokens

or similarly precise naming.

Recommended fields:

id UUID PRIMARY KEY

league_id UUID NOT NULL
league_season_id UUID if useful for authorization/context
league_member_id UUID NOT NULL

created_by_user_id UUID NOT NULL

token_hash TEXT NOT NULL UNIQUE

status TEXT NOT NULL
allowed values conceptually:

pending
redeemed
revoked
expired

created_at TIMESTAMPTZ NOT NULL DEFAULT now()
expires_at TIMESTAMPTZ NOT NULL

redeemed_at TIMESTAMPTZ
redeemed_by_user_id UUID

revoked_at TIMESTAMPTZ

Optional:
created_for_claim_type
or limited audit metadata if useful

Do NOT store the raw recovery token.

==================================================
7. TOKEN GENERATION
==================================================

Generate a cryptographically secure opaque token.

Use at least:

128 bits of entropy

Prefer:

256 bits

Do NOT use:

Math.random()
sequential IDs
member UUID as token
league UUID as token
predictable strings

Store only:

SHA-256(raw_token)

The raw token should exist only long enough to construct the recovery URL returned to the commissioner.

==================================================
8. TOKEN LIFETIME
==================================================

V1 recommendation:

24-hour expiration

If the codebase already has a security convention for temporary credentials, reuse it.

Expired token:
cannot redeem.

Commissioner may generate a new link.

Do not create permanent recovery links.

==================================================
9. SINGLE USE
==================================================

Token must become unusable immediately after successful redemption.

First successful redemption:

- validate
- transfer claim
- status = redeemed
- redeemed_at set
- redeemed_by_user_id set

reject as already used.

Transfer + redemption must be atomic.
