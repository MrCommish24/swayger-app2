# Swayger Phase 1 Planning Prompt: Make Gameday the Primary Product Experience

Review the current Swayger codebase and produce a detailed, implementation-ready plan for making **Swayger Gameday the primary user experience**, while preserving the existing 1v1 Swayger challenge system as a secondary feature.

Your job is to inspect the current implementation and produce a precise Phase 1 plan that could be approved before development begins.

---

# Background

The current Swayger application was originally built around 1v1 sports challenges.

The current 1v1 experience includes:

* Creating a challenge
* Inviting a specific opponent
* Accepting or countering a take
* Locking stakes
* Settling the result
* Generating a shareable receipt
* Tracking records and leaderboard results

The 1v1 product has experienced a cold-start problem. A user must create a challenge, identify an opponent, share the challenge, get the opponent to accept, and later return to settle the result.

Swayger Gameday Rooms have shown more promising engagement.

The Gameday experience includes:

* Rooms built around a live sporting event
* Direct room links
* Guest participation
* Pregame picks
* Halftime picks
* Fourth-quarter or clutch picks
* Pick locking
* Host controls
* Manual prop settlement
* Live leaderboard
* Final standings
* Shareable Gameday receipts

The product strategy is now:

> Use Gameday Rooms as the primary acquisition and participation experience. Preserve 1v1 challenges as a secondary feature that may later become a retention, rivalry, or post-Gameday mechanic.

The current codebase assessment indicates that the two systems are largely independent and that Gameday can likely become primary without rebuilding the entire application.

---

# Phase 1 objective

The immediate objective is:

> Make it easier for a user to discover a Gameday Room, join it, understand the current phase, submit picks, return for later phases, and view the leaderboard.

Phase 1 should primarily involve:

* Product hierarchy
* Navigation
* Homepage
* Room discovery
* Shared-link room entry
* Gameday phase clarity
* Empty states
* Analytics

Phase 1 should not attempt to solve every future Gameday need.

# Desired product hierarchy

The application should feel like:

> Swayger is a live sports prediction and competition experience built around Gameday Rooms. 1v1 challenges remain available for users who want direct head-to-head competition.

The likely hierarchy is:

## Primary

* Gameday
* Live and upcoming rooms
* Rooms the user has joined
* Open pick cards
* Leaderboards
* Final standings

## Secondary

* 1v1 challenges
* Create a 1v1 challenge
* Join a 1v1 challenge
* Challenge history
* 1v1 leaderboard
* Receipts

Do not assume these exact navigation names must be used. Recommend the clearest labels based on the existing routes and components.

---

# Desired primary user journey

The target user flow is:

1. User opens Swayger
2. User sees a live or upcoming Gameday Room
3. User selects the room
4. User sees the matchup, room status, game time, participant count, and current pick phase
5. User joins as a guest or authenticated user
6. User immediately makes picks if a card is open
7. User sees confirmation that picks were submitted
8. User understands when the next phase opens
9. User returns for halftime or fourth-quarter picks
10. User views the leaderboard and final standings

Every Phase 1 recommendation should support this flow.

# Step 13: Define acceptance criteria

Create specific acceptance criteria for the overall Phase 1 release.

At minimum, include:

## Navigation

* Gameday is the first and most prominent product destination.
* 1v1 challenges remain accessible.
* All existing direct challenge links continue to work.
* All existing room links continue to work.

## Home screen

* A user can see a live or upcoming room without navigating through Profile.
* The primary call to action directs users toward a Gameday Room.
* The page has a useful state when no room is live.

## Room discovery

* Public live rooms are visible.
* Upcoming rooms are visible if the current API supports them.
* A user can identify room status before entering.

## Joining

* A guest can join using a display name.
* An authenticated user can join without unnecessary duplicate steps.
* A user can reach the first open pick card quickly.

## Pick phases

* The current phase is obvious.
* The user can tell whether picks are open, locked, or submitted.
* The next expected action is clear.

## 1v1 preservation

* Users can create and join 1v1 challenges.
* Active challenges remain visible.
* Settlements and receipts continue to function.
* The 1v1 leaderboard remains accessible.

## Analytics

* The primary Gameday funnel can be measured.
* Existing event names are preserved where practical.
* New properties do not expose sensitive information.
