Begin the next Swayger Fantasy build phase:

PHASE 3 — MEMBER CLAIM + MEMBER FANTASY LEAGUE VIEW

The commissioner creation flow is complete and tested. Do not reopen the Phase 1/2 architecture.

The objective of this phase is simple:

A commissioner has already created a Fantasy League and entered the league members + team names.

Now another member should be able to open an invitation, identify which preloaded league seat belongs to them, claim that seat, and thereafter return to Swayger and see that Fantasy League as their own.

CORE MEMBER JOURNEY

Commissioner shares league invitation
→ member opens link
→ sees league identity immediately
→ signs in / creates account OR continues as guest where supported
→ sees preloaded league members + teams
→ chooses “That’s me”
→ confirms claim
→ lands in Fantasy League Hub as that member
→ future visits recognize them automatically

Example:

Food Pyramid — 2026 Fantasy Football

Who are you?

Darius — The Monstars
Mike — Sunday Scaries
Chris — Fourth & Long

Mike taps:

Mike — Sunday Scaries

Then confirm:

“This is me”

After successful claim:

Welcome to Food Pyramid
Mike — Sunday Scaries

The user should NOT have to re-enter their name or team name.

IMPORTANT IDENTITY RULE

A person and a fantasy team are separate concepts.

The user claims:

fantasy_league_members.id

NOT the fantasy_team record.

The UI should DISPLAY both person + team together for clarity:

Mike — Sunday Scaries

but the persistent identity claim attaches to the league-member record.

Do not change this architecture.

COPY CHANGE FROM COMMISSIONER SETUP

Clarify the existing commissioner field currently described as “Your name in this league.”

Preferred copy:

YOUR DISPLAY NAME

“The name other league members know you by.”

Example: Darius

Keep fantasy team name as a separate field:

FANTASY TEAM NAME

Example: The Monstars

Do not collapse display_name and team_name into one field.

MEMBER CLAIM ARCHITECTURE

Existing foundation:

fantasy_league_members
→ persistent person/seat in the league

fantasy_member_claims
→ maps authenticated user OR durable guest token to that persistent league member

fantasy_season_members
→ activates that persistent member for a season

fantasy_teams
→ season-specific fantasy team

fantasy_team_managers
→ links season member to fantasy team

Use these existing entities.

Do not create a duplicate member identity system.

INVITATION / ROUTING

Create a member-facing invitation path that can be shared by the commissioner.

Preferred shape can follow existing Swayger routing conventions, but conceptually it must resolve:

league
+ current season

and direct the user into the member claim flow.

Example conceptual URL:

/fantasy/join/:leagueId/:seasonId

If the project already has a better short-link/invite convention, use it and explain why.

The member must NOT need to know or enter a league ID/code manually if they arrived through the shared invitation.

CLAIM SCREEN

Before claim, show:

- League name
- sport
- season
- optional weekly reward if configured
- preloaded available member/team rows

Example:

FOOD PYRAMID
2026 Fantasy Football

Weekly Swayger Reward: $25

Who are you?

○ Darius — The Monstars
○ Mike — Sunday Scaries
○ Chris — Fourth & Long

Only seats eligible for claim should be selectable.

Think carefully about already-claimed seats.

Preferred MVP behavior:

- clearly show already-claimed seats as unavailable
- do not allow a second unrelated authenticated user/device to casually overwrite an existing claim
- preserve an admin/recovery path for future support work rather than solving every reassignment case in this phase

If an authenticated user already has the valid claim for one of these seats, auto-recognize them and bypass the seat-selection screen where safe.

AUTH + GUEST BEHAVIOR

Maintain low-friction entry.

If the current Swayger architecture supports durable guest identity cleanly:

- Signed-in user → create user_id claim
- Guest → create guest_token claim using the existing durable-device-token pattern

Do not invent a second guest-token mechanism if an existing Game Day mechanism can be safely reused.

If existing guest infrastructure is not suitable for persistent Fantasy claims, stop and report the gap before building a brittle workaround.

Account creation should NOT be mandatory merely to make Draft Day predictions unless there is a hard technical/security reason.

However:

- authenticated claims should work across devices after login
- guest claims may reasonably be device-specific
- explain that distinction in the implementation report

CLAIM SAFETY / AUTHORIZATION

A member must not be able to claim someone from an unrelated league by manipulating IDs.

The claim operation must validate:

1. league_member belongs to leagueId
2. seasonId belongs to leagueId
3. league_member is active in the target season through fantasy_season_members
4. if selecting/displaying a team, the team relationship belongs to the same season
5. caller is not overwriting an active claim belonging to another identity without an explicit supported recovery process

Use an atomic database operation if claim creation requires multiple coordinated writes.

If only fantasy_member_claims is written, a single safe insert/upsert may be sufficient — inspect first.

Do not use fantasy_leagues.created_by for member identity.

MEMBER FANTASY LEAGUE VIEW

After a successful claim, route to the existing Fantasy League Hub.

The hub should become role-aware.

For a normal member, show:

- League name
- sport / season
- their display name + team prominently
- weekly reward if configured
- league member/team list
- Draft Day “Coming Soon” / future competition area

Do NOT expose commissioner setup/admin actions to a normal member.

For the commissioner, preserve existing commissioner information and controls.

The page should feel like:

“My fantasy league on Swayger”

not:

“commissioner database setup.”

HOME DISCOVERABILITY

Once a member has successfully claimed a Fantasy League, GET /api/fantasy/leagues or the appropriate member-facing query must allow that league to appear in the existing:

MY FANTASY LEAGUES

section on the main Swayger home tab.

Important:

The current league list was originally built around commissioner-created leagues.

Update the logic so My Fantasy Leagues means:

“Fantasy leagues I belong to”

not merely:

“Fantasy leagues I created.”

A member such as Mike should see Food Pyramid on his home screen after claiming his seat.

Do not break the commissioner experience.
