We are building the next major Swayger Pick Card improvement:

INCREMENTAL MATCHUP-BY-MATCHUP SETTLEMENT

PRODUCT CONTEXT

Swayger Discord Pick Cards are now working end to end:

- commissioner creates a Pick Card in Discord
- actual matchups display publicly
- participants click into Swayger and make structured picks
- submitted picks are posted publicly back into Discord
- material edits are also posted publicly
- commissioner manually locks the card
- after lock, picks cannot change

The next problem is settlement.

In the existing native Madden Discord workflow, a commissioner may eventually mark a participant with a simple ❌ if one of their picks lost.

That is easy, but weak:

- participants cannot see which pick was wrong
- commissioner must manually inspect everybody’s picks
- results are not structured
- partial progress is not visible
- late games cannot update dynamically

Swayger can do materially better.

CORE PRODUCT PRINCIPLE

The commissioner should resolve each matchup ONCE.

Swayger should automatically apply that result across every participant.

If a Pick Card has 7 matchups and 16 participants, the commissioner should resolve 7 game outcomes — not manually audit 112 individual picks.

SETTLEMENT MODEL

Keep these three concepts distinct:

1. LOCK
   - no more participant edits

2. SETTLE
   - commissioner records the result of ONE matchup
   - can happen one matchup at a time as games finish

3. FINALIZE
   - only after all required matchups are settled
   - calculates/finalizes final standings

Desired lifecycle:

OPEN
↓
LOCKED
↓
Matchup 1 settled
Matchup 2 unsettled
Matchup 3 settled
...
↓
ALL MATCHUPS SETTLED
↓
FINALIZE
↓
FINAL STANDINGS

DO NOT require all matchups to be settled at once.

EXISTING ARCHITECTURE

We already have Game Day prop settlement concepts and an endpoint historically shaped like:

PATCH /api/gameday/props/:propId/settle

and room finalization.

Before changing architecture, inspect the existing settlement implementation and reuse it where correct.

Do NOT build an unnecessary parallel settlement system if current prop-level settlement already supports the required semantics.

This task is specifically about making the existing system support this Pick Card workflow cleanly.

SCOPE

This V1 applies to:

source = discord
sport = madden
template_type = weekly_pick_card

But avoid unnecessarily hardcoding behavior if the existing Game Day settlement model can support it generically.

COMMISSIONER CAPABILITY NEEDED

The backend must expose enough structured data for a future Discord command:

/swayger gameday resolve

to:

1. identify the active Pick Card
2. list unresolved matchups
3. choose one matchup
4. choose the winning option
5. settle that matchup
6. return updated progress
7. repeat later for another matchup

Do NOT build the external Discord bot command in this task.

BACKEND SETTLEMENT REQUIREMENTS

For each matchup/prop:

status should clearly distinguish:

- open/unsettled
- settled

and expose:

- prop_id
- question / matchup label
- answer options
- current settlement status
- correct_answer, if settled
- display order

Example:

{
  "prop_id": "uuid",
  "matchup_label": "Bears vs Jags",
  "options": ["Bears", "Jags"],
  "status": "open",
  "correct_answer": null,
  "display_order": 0
}

After settlement:

{
  "prop_id": "uuid",
  "matchup_label": "Bears vs Jags",
  "options": ["Bears", "Jags"],
  "status": "settled",
  "correct_answer": "Bears",
  "display_order": 0
}

VALIDATION

A settlement must:

- be commissioner/host authorized
- only accept one of the prop’s valid answer options
- reject malformed/unknown answer values
- reject cross-room prop access
- preserve guild/room security
- be idempotent when setting the same correct answer again

CORRECTIONS

Commissioners make mistakes.

We need a safe V1 correction path.

If an already-settled matchup is changed from:

Bears

to:

Jags

the system should:

- permit the correction only for an authorized host/admin
- recalculate affected participant correctness
- preserve an audit trail / settlement event
- return that the result was corrected
- NOT require database surgery

Do not build a complicated approval workflow.

Simple authorized correction + auditability is enough.

PARTICIPANT PICK RESULT STATE

Each participant pick should now be able to render one of:

PENDING / UNSETTLED
CORRECT
INCORRECT

Example participant card:

✅ Bears
✅ Ravens
⏳ Giants
❌ Raiders

Use existing gameday_picks.is_correct if appropriate.

Semantics:

- prop not settled → is_correct should remain null
- prop settled + selected correct option → true
- prop settled + selected wrong option → false

Do not prematurely mark unsettled picks false.

PARTICIPANT WEB EXPERIENCE

Update the Pick Card participant/receipt view after lock so that each matchup clearly shows status.

Desired visual concept:

Who wins: Bears vs Jags?
✅ Bears (you)

Who wins: Ravens vs Bengals?
❌ Ravens (you)

Who wins: Giants vs Cowboys?
⏳ Giants (you)

The exact styling may follow existing design conventions.

Important:

The participant should be able to tell WHICH pick is right/wrong/pending.

Do not only show a whole-card win/loss indicator.

LOCKED STATE COPY

The current web copy still includes stale reveal language such as:

"Picks are locked. Receipts are revealed."

That is no longer correct because Discord picks are publicly visible before lock.

Update the locked-state copy to something like:

Picks are locked.
No more changes. Results will update as matchups are settled.

Keep "Final Receipts" as the later completed state if appropriate.

SETTLEMENT PROGRESS

Expose card-level settlement progress.

Example:

{
  "total_matchups": 7,
  "settled_matchups": 3,
  "remaining_matchups": 4,
  "all_settled": false
}

This is important for the future Discord commissioner flow.

FINALIZATION RULE

A Pick Card should not finalize until all required playable matchups are settled.

If finalization is attempted early:

return a clear response such as:

{
  "error": "Cannot finalize while matchups remain unsettled",
  "remaining_matchups": 2
}

Do not silently finalize incomplete cards.

When all matchups are settled:

- finalization remains explicit
- calculate existing leaderboard/final standings
- preserve current scoring_mode = all_correct behavior unless existing architecture already defines something else

For all_correct:

- participant is perfect only if every required pick is correct
- any false pick means they did not hit the full card
- pending state exists until all required props are settled

Do not invent new scoring modes.

COMMISSIONER SETTLEMENT QUEUE API

We need a clean contract for Claude.

Prefer extending existing room detail/admin APIs if clean.

Otherwise expose a small bot-authenticated endpoint such as:

GET /api/gameday/bot/rooms/:roomId/settlement

or equivalent existing architecture.

It should return:

- room_id
- room_code
- room_name
- card_id
- card status
- total_matchups
- settled_matchups
- remaining_matchups
- all_settled
- matchups ordered by display_order

For each matchup:

- prop_id
- matchup_label
- options
- status
- correct_answer
- display_order

Do NOT return unnecessary participant PII.

SETTLE API

Prefer existing:

PATCH /api/gameday/props/:propId/settle

if it already satisfies the contract.

If bot auth currently cannot call it, add the smallest appropriate bot-authenticated path or authorization support.

The future Discord bot needs to be able to send:

Do NOT overbuild a new audit subsystem.
