# NFL Sunday Slate V1 — Replit Build Prompt

You are working in the main Swayger Replit project.

The existing NFL Game Day V1 build is complete and should remain intact.

That existing build should now be treated as the **NFL Single Game** format.

NFL Single Game is useful for:

* Thursday Night Football
* Sunday Night Football
* Monday Night Football
* Playoffs
* Super Bowl
* Madden-style single-game activations later

Do not replace, undo, or redesign the existing NFL Single Game work.

The new task is to add a second NFL format:

# NFL Sunday Slate V1

The objective is to support the way NFL Sundays actually work: multiple games across the early and late windows, with a final Sunday Night Football card.

This should be built as an extension of the existing Game Day architecture, not a new engine.

# 2. Add NFL room format/template type

NFL now needs two formats:

1. `nfl_single_game`
2. `nfl_sunday_slate`

Use the project’s existing naming conventions where possible.

Preferred approach:

* Keep `sport = "nfl"`
* Add a format/template discriminator such as:

  * `template_type = "nfl_single_game" | "nfl_sunday_slate"`
  * or `game_format = "single_game" | "sunday_slate"`

Use whichever fits the current architecture best.

Do not create a second Game Day system.

If a schema migration is needed, make it additive and backwards-compatible.

Existing NFL rooms should behave as single-game rooms.

Legacy callers that send only `sport: "nfl"` may continue defaulting to the current NFL Single Game template unless the host explicitly selects Sunday Slate.

Legacy callers that omit `sport` should continue preserving existing NBA/default behavior.

---

# 3. Product definition

NFL Sunday Slate V1 is a manually curated, cross-game prediction room.

It should allow the host/admin to create a room like:

> NFL Sunday Slate — Week 1

The room should cover:

* Early Sunday games
* Late Sunday games
* Sunday Night Football

Use the existing three-card Game Day structure internally, but apply Sunday Slate labels.

Internal phase reuse is preferred:

| Existing internal phase | Sunday Slate label |
| ----------------------- | ------------------ |
| `pregame`               | Early Slate Picks  |
| `halftime`              | Late Slate Picks   |
| `fourth`                | Sunday Night Picks |

Do not create new phase identifiers unless absolutely necessary.

---

# 4. Default pick counts

NFL Sunday Slate should use compact player-facing cards:

* Early Slate Picks: 8 default picks
* Late Slate Picks: 5 default picks
* Sunday Night Picks: 3 default picks

Do not show 20+ questions on one card.

A larger prop library is fine, but the default room should stay manageable.

---

# 5. Admin burden principle

This is a pilot-stage feature.

The admin/host should be able to:

* Set up the Sunday Slate room in roughly 20 minutes or less
* Settle the room in roughly 15 minutes or less
* Verify outcomes from normal final scores and stat leaderboards
* Avoid hunting through obscure play-by-play details

Do not create props that require watching every game live.

Do not create props that require subjective judgment.

Do not create props that require obscure stat interpretation.

This is important because the admin is currently me, and this must be manageable before automation is justified.

---

# 6. Manual settlement model

Preserve manual host/admin settlement.

NFL Sunday Slate V1 should be settleable by one admin using final scores and stat leaderboards.

The app may provide optional settlement reference support, but the host/admin remains the source of truth.

Every settlement action must still require the host/admin to choose or confirm the correct answer.

Do not auto-settle.

Do not create props that require exact lock-time context unless that context is already stored.

Avoid slate-wide “next score” style props unless they are tied to a single Sunday Night game or otherwise easy to verify.

For this reason, Sunday Slate props should focus on:

* final player stat leaders
* final team scores
* final game margins
* final game totals
* Sunday Night single-game outcomes

# 9. Editable answer options

NFL Sunday Slate V1 must support editable answer options.

Unlike single-game NFL props, Sunday Slate props are not just Team A vs Team B.

The host/admin needs a clean way to populate and edit candidates such as:

* QB candidates
* RB candidates
* WR/TE candidates
* Team candidates
* Game candidates
* Sunday Night teams

For V1, candidate options should be manually entered or edited by the host/admin.

Do not require an API to populate candidates.

This matters because of:

* injuries
* inactive players
* changing matchups
* better weekly candidates
* host judgment

The host/admin should be able to change answer options before creating/publishing the room.

If an existing sports data source can safely provide optional suggestions without significant extra work, document that as a future enhancement, but it should not block V1.

# 10. “Other” option

For leader-style props, include an `Other` option by default.

Examples:

* Which QB throws for the most passing yards?
* Which player rushes for the most yards?
* Which player has the most receiving yards?
* Which team scores the most points?
* Which team allows the fewest points?

This keeps the prop fair when someone outside the curated candidate list wins.

For props where answer options are selected games, do not add `Other` unless the prop intentionally allows unlisted games.

# 14. Tie handling

For Sunday Slate leader props, ties are possible.

Support tie settlement in a simple, fair way.

Preferred V1 behavior:

* If multiple candidates tie for the lead and one or more tied candidates are listed as answer options, the host should be able to select multiple correct answers if the existing settlement model supports multi-correct.
* If multi-correct settlement is not supported, add a `Tie / Multiple tied` answer option where appropriate.
* If that is too invasive, document the limitation and avoid forcing the host to choose one incorrect winner.

Do not make major scoring-engine changes if avoidable.

At minimum:

* Do not force the host/admin to choose one player/team if the actual result is a tie.
* The settlement UI must have a valid path for tied outcomes.
