# 1. Database-backed idempotency

Replace or supplement the current in-memory idempotency cache with a durable database-backed mechanism.

In-memory idempotency alone is insufficient because it is lost during:

- Server restart
- Redeployment
- Process crash
- Multiple application instances
- Delayed mobile retry
- Browser refresh

## Schema proposal

Before applying any migration, inspect existing tables and migrations to determine whether an admin operations or idempotency table already exists.

If no suitable table exists, propose the smallest additive table needed.

A likely structure is:

- `id`
- `idempotency_key`
- `operation_id`
- `operation_type`
- `operator_identifier`
- `group_key`
- `request_hash`
- `status`
- `result_json`
- `error_json`
- `created_at`
- `started_at`
- `completed_at`

Required constraints:

- Unique constraint on `idempotency_key`
- Index on `operation_id`
- Index on `created_at`
- Optional compound validation involving operator and operation type if appropriate

Do not store:

- Admin token
- Secrets
- Full participant data
- Unnecessary pick details

## Required behavior

When a global settlement request arrives:

### New key

- Validate the request
- Create an `in_progress` idempotency record atomically
- Process the operation
- Store the final response
- Mark the record `completed` or `failed`

### Existing key with identical request hash

- If completed, return the original stored result
- If failed, return the stored failure result or a clearly documented retry behavior
- If in progress, return a safe processing response rather than running the operation again

### Existing key with different request hash

Reject the request.

Return an error such as:

`IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST`

The request hash should be derived from stable request fields such as:

- Group key
- Canonical answer
- Sorted prop IDs
- Expected prop count
- Authorized operator identity

Do not include volatile fields.

## Atomic claim requirement

The idempotency claim must be atomic.

Two simultaneous requests with the same key must not both begin processing.

Use the database unique constraint and appropriate insert/upsert behavior rather than:

1. Querying for the key
2. Finding nothing
3. Inserting later

That sequence would preserve a race condition.

## Migration approval checkpoint

If a migration is required:

- Show the exact SQL
- Explain rollback
- Confirm it is additive and non-destructive
- Stop for approval before applying it

Do not silently migrate production.

# 2. Partial-failure behavior

Document exactly what happens if a multi-prop settlement begins and an unexpected failure occurs after one or more props have already settled.

Example:

- Prop 1 succeeds
- Prop 2 succeeds
- Prop 3 fails

Determine whether the current architecture can use a single database transaction across the entire group.

## Preferred behavior

If practical with the current Supabase architecture:

- Settle the entire group atomically
- All props succeed or no props change

Do not introduce a large or risky transactional redesign solely to satisfy this preference.

## Acceptable fallback

If cross-room atomicity is not practical:

- Preserve successful prop settlements
- Report every successful, skipped, and failed prop
- Mark the operation as `partial_success`
- Keep failed props visible in the queue
- Ensure retrying is safe
- Ensure already-settled props are not treated as new work
- Provide room and prop identifiers for failures
- Record one shared operation ID across all audit events
- Never return a generic success or failure that hides partial mutation

The client must clearly distinguish:

- Success
- Partial success
- Stale group
- Complete failure
- Idempotent replay

## Strict stale behavior

If the reviewed prop set has changed before any settlement begins:

- Reject the entire request
- Settle nothing
- Require the admin to refresh

Do not interpret stale detection as a partial-failure scenario.

# 6. Failure and retry tests

Run these tests against the durable idempotency implementation and actual write endpoint.

## Double tap

Send the same operation twice in parallel with the same idempotency key.

Expected:

- Only one operation claims the key
- One logical settlement occurs
- Both callers receive consistent results
- No duplicate logical audit operation

## Restart replay

Complete an operation, restart the backend, and resend the same request.

Expected:

- Stored result is returned
- No settlement is reprocessed
- No second audit operation is created

## Key reuse with changed payload

Reuse the key with a different answer or prop set.

Expected:

- Rejected
- Nothing changes

## Stale group

Load a group, then settle one included prop individually before submitting globally.

Expected:

- Entire operation rejected as stale
- No remaining props settle
- UI instructs the admin to refresh

## Runtime partial failure

Simulate or induce a failure after at least one prop processes, if the architecture cannot provide group-level atomicity.

Expected:

- Accurate partial-success response
- Successful props remain correct
- Failed props remain visible
- Retry behavior is safe
- Audit and operation records are complete

## Unauthorized access

Verify:

- No token → rejected
- Invalid token → rejected
- Normal participant → rejected
- Room host without global-admin authorization → rejected
- Valid global admin → accepted when flags permit

## Feature flags

Verify:

- Backend flag off → write endpoint unavailable or 503
- UI flag off → no settlement controls
- Backend on, UI off → endpoint remains protected and UI remains read-only
- UI on, backend off → clear failure; no mutation
