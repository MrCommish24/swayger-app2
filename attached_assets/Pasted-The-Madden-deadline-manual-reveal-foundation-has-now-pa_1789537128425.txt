The Madden deadline/manual-reveal foundation has now passed production smoke testing.

We are ready to build the next V1 feature:

DISCORD PARTICIPATION ACTIVITY

PRODUCT GOAL

Today Madden league members often make picks directly in Discord.

That visible activity creates:
- social proof
- FOMO
- conversation
- evidence that other league members are participating

Swayger moves the actual picks into the web app, so we need to feed PARTICIPATION back into the originating Discord channel.

V1 BEHAVIOR

When a participant FIRST completes all required picks for a Discord-created Madden Weekly Pick Card:

create one persistent Discord activity event.

The future Discord bot will post something like:

🔥 Darius is in.

4 players have made their picks.
Lock it in and stand on it.

IMPORTANT:

Do NOT reveal:
- selected teams
- bonus answer
- receipt
- any actual picks

For V1, use the participant's Swayger display name.

Do NOT add Discord identity linking yet.

COMPLETION DEFINITION

A participant is complete when they have a valid saved pick for every required playable prop on the Madden Weekly Pick Card.

This includes:

- every matchup prop
- enabled bonus prop when it requires a participant choice

Examples:

3 matchups + enabled bonus
→ participant needs 4 saved picks

3 matchups + disabled bonus
→ participant needs 3 saved picks

The event must be created only on the transition:

incomplete → complete

ONE EVENT PER PARTICIPANT PER ROOM

Do NOT create another event if the participant:

- refreshes
- returns later
- resubmits identical picks
- edits one of their picks before the deadline
- changes a pick and remains complete

Participation should generate one social notification per participant per room.

DEADLINE / LOCK INTERACTION

Respect the production behavior already implemented:

- picks editable before deadline
- picks automatically become non-editable at deadline
- commissioner lock remains manual reveal
- this activity event is independent of commissioner lock

A participant who becomes complete before the deadline produces the event immediately.

Do not emit additional participation events at deadline or lock.

ROOM ELIGIBILITY

Generate these events ONLY when all are true:

- room.source = "discord"
- room.sport = "madden"
- room.template_type = "weekly_pick_card"
- room.discord_guild_id exists
- room.discord_channel_id exists

Do NOT add this behavior to:
- web-created Madden cards
- NFL
- NBA
- Fantasy
- Sunday Slate
- other Game Day formats

yet.

OUTBOX ARCHITECTURE

The Swayger backend must NOT post directly to Discord.

Do not give the backend a Discord bot token.

Create the smallest persistent Discord activity/outbox mechanism that the external Swayger Discord bot can poll.

Prefer a database-backed structure so delivery survives:
- backend restart
- bot restart
- temporary Discord failure

Suggested event type:

madden_picks_completed

Use the repository's naming conventions if a better existing convention exists.

EVENT DATA

Each event should contain enough information for the bot to deliver the message without accessing participant selections.

At minimum:

- id
- event_type
- room_id
- room_code
- room_name / week_label
- discord_guild_id
- discord_channel_id
- participant identifier needed for idempotency
- participant_display_name
- completed_participant_count
- created_at
- delivered_at or equivalent delivery status

Do NOT persist participant pick selections into the event.

IDEMPOTENCY

Enforce one:

madden_picks_completed

event per:

room + participant

Prefer database-level uniqueness where practical.

Do not rely solely on process memory.

COMPLETED PARTICIPANT COUNT

The event should include the number of unique participants who have completed that room at the time this event is generated.

Example:

Darius completes first:
completed_participant_count = 1

Mike completes next:
completed_participant_count = 2

Chris completes next:
completed_participant_count = 3

Do not count:
- partial participants
- duplicate completions
- refreshes
- edits after completion

BOT DELIVERY API

Add bot-authenticated, guild-scoped endpoints using the existing Game Day bot security conventions.

Need two capabilities:

1. FETCH PENDING EVENTS

The bot can request pending activity events for the invoking guild.

Requirements:
- valid GAMEDAY_BOT_API_KEY
- X-Discord-Guild-ID required
- return only events where event.discord_guild_id matches
- pending/unacknowledged events only
- reasonable limit
- oldest-first preferred

2. ACKNOWLEDGE DELIVERY

After Discord successfully posts the activity message:

- bot acknowledges the specific event
- valid GAMEDAY_BOT_API_KEY required
- X-Discord-Guild-ID required
- event guild must match header guild
- event becomes delivered
- event is no longer returned by pending fetch

Do not acknowledge on fetch.

If Discord posting fails:
- event remains pending
- bot can retry later

Guild isolation must fail closed.

PICK WRITE INTEGRATION

Inspect the existing shared Game Day pick submission/upsert path.

After a successful pick write:

1. Check whether the eligible Madden participant is now complete.
2. If not complete:
   do nothing.
3. If complete:
   check whether that room+participant already has a completion event.
4. If none:
   create the event.
5. If already present:
   do nothing.

Do not let event-generation failure corrupt or roll back an otherwise valid participant pick unless the existing transaction model makes atomic handling clearly safer.

Explain your chosen failure behavior.

PARTICIPANT IDENTITY

Support both:
- authenticated participants
- guest participants

Use the existing participant identity model for idempotency.

For message display, use the best existing participant/display-name field already shown in Game Day.

Do not invent Discord usernames.

ARCHIVED / FINALIZED ROOMS

Do not generate new participation events for:
- archived rooms
- finalized rooms
- cards where picks are closed

Normal deadline/lock write protection should already prevent most of this, but preserve sensible defensive checks.

MIGRATION

If a new table/index/migration is required:

- create it cleanly
- make it safe for existing production data
- do not mutate historical rooms/picks
- do not backfill fake events
